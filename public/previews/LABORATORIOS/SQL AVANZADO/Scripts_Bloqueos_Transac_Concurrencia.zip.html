Scripts_Bloqueos_Transac_Concu copy/LEEME_1.txt
=======================================================================
 Bases de Datos 2 · Concurrencia, transacciones y bloqueos
 Práctica de dos horas sobre Oracle Autonomous Database (Always Free)
=======================================================================

QUÉ NECESITA CADA PAREJA
  · Un usuario propio en la base (P01, P02, ...), con su contraseña
  · DOS sesiones abiertas al mismo tiempo, con el MISMO usuario
  · Los archivos 02_sesion_A.sql y 02_sesion_B.sql, uno en cada sesión

-----------------------------------------------------------------------
ANTES DE LA CLASE  (docente)
-----------------------------------------------------------------------
1. Cree la Autonomous Database Always Free en OCI
     Menú → Oracle Database → Autonomous Database → Create
     Workload type: Transaction Processing
     Marque "Always Free"
     Guarde la contraseña de ADMIN

2. Conéctese como ADMIN por Database Actions
     Botón "Database actions" → "SQL"

3. Ejecute 00_admin_crear_usuarios.sql
   Crea P01..P15, les da permisos, cuota y los habilita en Database
   Actions. Ajuste el número de parejas en la variable del script.

4. Anote la URL de Database Actions y repártala con los usuarios y
   contraseñas. La URL se ve así:
     https://<algo>.adb.<region>.oraclecloudapps.com/ords/sql-developer

-----------------------------------------------------------------------
CÓMO ABRIR DOS SESIONES  (estudiantes)
-----------------------------------------------------------------------
OPCIÓN A — SQLcl  (la más confiable, recomendada)
     Descargue el wallet desde OCI (el docente lo comparte) y abra DOS
     terminales:
        sql /nolog
        SQL> set cloudconfig wallet.zip
        SQL> connect P01@basedatos_high
     Repita en la segunda terminal.
     En SQLcl el autocommit viene APAGADO: es lo que queremos.

OPCIÓN B — Database Actions en el navegador
     Abra la URL en una ventana normal y otra vez en una ventana de
     incógnito (o en otro navegador). Son dos sesiones distintas.
     IMPORTANTE: en cada hoja de trabajo, apague el autocommit.
        Menú de la hoja → Settings → Autocommit → OFF
     Si no lo apaga, cada sentencia confirma sola y NINGÚN demo funciona.

ANTES DE EMPEZAR, COMPRUEBE QUE SON DOS SESIONES DE VERDAD:
   En cada ventana ejecute:
        SELECT SYS_CONTEXT('USERENV','SID') AS sid FROM dual;
   Los dos números deben ser DISTINTOS. Si son iguales, no tiene dos
   sesiones y ningún ejercicio de bloqueo va a funcionar.

-----------------------------------------------------------------------
ORDEN DE LOS ARCHIVOS
-----------------------------------------------------------------------
  00_admin_crear_usuarios.sql .... solo el docente, una vez
  01_setup_pareja.sql ............ cada pareja, en UNA de las dos sesiones
  02_sesion_A.sql ................ la sesión A, paso a paso
  02_sesion_B.sql ................ la sesión B, paso a paso
  03_diagnostico.sql ............. ver los bloqueos mientras ocurren
  04_retos.sql ................... ejercicios para resolver en pareja
  99_limpieza.sql ................ al terminar

Los archivos 02 están sincronizados: cada bloque dice PASO 1, PASO 2, y
hay que ejecutarlos ALTERNANDO entre las dos ventanas, en orden. Nunca
corra un archivo 02 completo de una sola vez.

-----------------------------------------------------------------------
SOBRE LOS PERMISOS DE MONITOREO
-----------------------------------------------------------------------
Las consultas de 03_diagnostico.sql leen V$SESSION y V$LOCK. En
Autonomous Database eso funciona sin problema con el usuario ADMIN.
Para los usuarios de la práctica puede fallar por permisos: en ese caso
el docente proyecta el monitoreo desde su sesión de ADMIN mientras las
parejas trabajan. El script trae las dos alternativas.

-----------------------------------------------------------------------
SI ALGO SE TRABA
-----------------------------------------------------------------------
· Una sesión que quedó bloqueada y no responde: haga ROLLBACK en la OTRA.
· Si perdió el control, el docente puede liberar desde ADMIN:
      ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE;
· Al cerrar la ventana del navegador, la sesión no siempre muere de
  inmediato: puede seguir bloqueando unos minutos.

  END LOOP;
END;

-- =====================================================================
-- Bases de Datos 2 · Concurrencia, transacciones y bloqueos
-- 03_diagnostico.sql — ver los bloqueos mientras están ocurriendo
--
-- Estas consultas leen vistas V$. Con el usuario ADMIN de la Autonomous
-- Database funcionan siempre. Con los usuarios de la práctica pueden
-- fallar por permisos: en ese caso el docente las proyecta.
-- =====================================================================

SET LINESIZE 220
SET PAGESIZE 100

-- ---------------------------------------------------------------------
-- 1. La consulta que responde “¿quién me está bloqueando?”
-- ---------------------------------------------------------------------
SELECT s.sid,
       s.serial#,
       s.username,
       s.status,
       s.blocking_session        AS bloqueado_por,
       s.event,
       s.seconds_in_wait        AS segundos_esperando,
       s.sql_id
  FROM v$session s
 WHERE s.username LIKE 'P%'
 ORDER BY s.blocking_session NULLS FIRST, s.sid;
--> La sesión con BLOQUEADO_POR lleno es la víctima.
--  El valor de esa columna es el SID de quien la tiene detenida.


-- ---------------------------------------------------------------------
-- 2. El árbol de bloqueos, cuando hay varios encadenados
-- ---------------------------------------------------------------------
SELECT LPAD(' ', 2*(LEVEL-1)) || s.sid AS jerarquia,
       s.username, s.status, s.event, s.seconds_in_wait
  FROM v$session s
 START WITH s.blocking_session IS NULL
        AND s.sid IN (SELECT blocking_session FROM v$session
                       WHERE blocking_session IS NOT NULL)
CONNECT BY PRIOR s.sid = s.blocking_session
 ORDER SIBLINGS BY s.sid;
--> Muy útil cuando media aplicación se detiene: muestra la sesión raíz
--  que está deteniendo a todas las demás.


-- ---------------------------------------------------------------------
-- 3. Qué está bloqueado exactamente
-- ---------------------------------------------------------------------
SELECT l.sid,
       s.username,
       l.type,
       CASE l.type WHEN 'TX' THEN 'transacción (fila)'
                   WHEN 'TM' THEN 'tabla (DML)'
                   ELSE l.type END          AS significado,
       DECODE(l.lmode, 0,'ninguno', 1,'null', 2,'RS', 3,'RX',
                       4,'S', 5,'SRX', 6,'X (exclusivo)')  AS modo_que_tiene,
       DECODE(l.request, 0,'-', 1,'null', 2,'RS', 3,'RX',
                         4,'S', 5,'SRX', 6,'X (exclusivo)') AS modo_que_pide,
       o.object_name
  FROM v$lock l
  JOIN v$session s ON s.sid = l.sid
  LEFT JOIN dba_objects o ON o.object_id = l.id1 AND l.type = 'TM'
 WHERE s.username LIKE 'P%'
   AND l.type IN ('TX','TM')
 ORDER BY l.sid, l.type;
--> TX con modo X = tiene filas bloqueadas.
--  TX con request 6 = está esperando una fila de otro.
--  TM = bloqueo de tabla; aparece siempre que hay DML, y en modo fuerte
--  cuando falta el índice de una llave foránea.


-- ---------------------------------------------------------------------
-- 4. Transacciones abiertas y cuánto UNDO están gastando
-- ---------------------------------------------------------------------
SELECT s.sid, s.username,
       t.start_time,
       t.used_ublk  AS bloques_undo,
       t.used_urec  AS registros_undo,
       t.status
  FROM v$transaction t
  JOIN v$session s ON s.saddr = t.ses_addr
 WHERE s.username LIKE 'P%'
 ORDER BY t.start_time;
--> Una transacción abierta hace horas es casi siempre un error: alguien
--  olvidó el COMMIT, o dejó una pantalla abierta en medio de la
--  transacción. Es la causa clásica del “snapshot too old”.


-- ---------------------------------------------------------------------
-- 5. La sentencia que está ejecutando quien bloquea
-- ---------------------------------------------------------------------
SELECT s.sid, s.username, q.sql_text
  FROM v$session s
  JOIN v$sql q ON q.sql_id = s.prev_sql_id
 WHERE s.sid IN (SELECT blocking_session FROM v$session
                  WHERE blocking_session IS NOT NULL);
--> Ojo: se usa PREV_SQL_ID, no SQL_ID. Quien bloquea normalmente ya
--  terminó su sentencia y está inactivo, esperando un COMMIT que nadie
--  hizo.


-- ---------------------------------------------------------------------
-- 6. Cuántos interbloqueos ha habido
-- ---------------------------------------------------------------------
SELECT name, value FROM v$sysstat
 WHERE name IN ('enqueue deadlocks','enqueue waits','enqueue timeouts');


-- ---------------------------------------------------------------------
-- 7. Liberar una sesión atascada  (solo el docente, como ADMIN)
-- ---------------------------------------------------------------------
-- Primero identifique el sid y el serial# con la consulta 1, y luego:
--
--   ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE;
--
-- En Autonomous Database también sirve:
--   BEGIN
--     DBMS_CLOUD_ADMIN... -- no aplica
--   END;
-- Use siempre ALTER SYSTEM KILL SESSION.
-- Matar la sesión deshace su transacción: el rollback puede tardar.

-- =====================================================================
-- Bases de Datos 2 · Concurrencia, transacciones y bloqueos
-- 00_admin_crear_usuarios.sql
--
-- LO EJECUTA EL DOCENTE, como ADMIN, en la Autonomous Database.
-- Crea un usuario por pareja, con permisos para crear sus propias
-- tablas y para entrar por Database Actions.
--
-- Ejecutar UNA sola vez, antes de la clase.
-- =====================================================================

SET SERVEROUTPUT ON
SET LINESIZE 200

-- ---------------------------------------------------------------------
-- Configuración: cuántas parejas y con qué contraseña
--   La política de Autonomous exige entre 12 y 30 caracteres,
--   al menos una mayúscula, una minúscula y un dígito, sin comillas.
-- ---------------------------------------------------------------------
DECLARE
  n_parejas   PLS_INTEGER := 15;
  v_usuario   VARCHAR2(30);
  v_clave     VARCHAR2(60);
BEGIN
  FOR i IN 1 .. n_parejas LOOP
    v_usuario := 'P' || TO_CHAR(i, 'FM00');
    v_clave   := 'Bosque2026_' || v_usuario;      -- ej: Bosque2026_P01

    -- Si el usuario ya existe, se elimina y se vuelve a crear
    BEGIN
      EXECUTE IMMEDIATE 'DROP USER ' || v_usuario || ' CASCADE';
      DBMS_OUTPUT.PUT_LINE('Recreando ' || v_usuario);
    EXCEPTION WHEN OTHERS THEN NULL;
    END;

    EXECUTE IMMEDIATE 'CREATE USER ' || v_usuario ||
                      ' IDENTIFIED BY "' || v_clave || '"';
    EXECUTE IMMEDIATE 'GRANT CONNECT, RESOURCE TO ' || v_usuario;
    EXECUTE IMMEDIATE 'ALTER USER ' || v_usuario || ' QUOTA 200M ON DATA';

    -- Habilita el usuario en Database Actions (necesario en ADB para
    -- que pueda entrar por el navegador con su propio usuario)
    BEGIN
      ORDS_ADMIN.ENABLE_SCHEMA(
        p_enabled             => TRUE,
        p_schema              => v_usuario,
        p_url_mapping_type    => 'BASE_PATH',
        p_url_mapping_pattern => LOWER(v_usuario),
        p_auto_rest_auth      => TRUE);
    EXCEPTION WHEN OTHERS THEN
      DBMS_OUTPUT.PUT_LINE('  Aviso ORDS en ' || v_usuario || ': ' || SQLERRM);
    END;

    DBMS_OUTPUT.PUT_LINE('OK  ' || RPAD(v_usuario, 6) || '  clave: ' || v_clave);
  END LOOP;
  COMMIT;
END;
/

-- ---------------------------------------------------------------------
-- Permisos de monitoreo (opcional)
--   Permite que las parejas vean sus propios bloqueos. Si falla, no pasa
--   nada: el docente proyecta el monitoreo desde ADMIN.
-- ---------------------------------------------------------------------
DECLARE
  n_parejas PLS_INTEGER := 15;
  v_usuario VARCHAR2(30);
BEGIN
  FOR i IN 1 .. n_parejas LOOP
    v_usuario := 'P' || TO_CHAR(i, 'FM00');
    BEGIN
      EXECUTE IMMEDIATE 'GRANT SELECT ON SYS.V_$SESSION TO ' || v_usuario;
      EXECUTE IMMEDIATE 'GRANT SELECT ON SYS.V_$LOCK TO '    || v_usuario;
      EXECUTE IMMEDIATE 'GRANT SELECT ON SYS.V_$TRANSACTION TO ' || v_usuario;
    EXCEPTION WHEN OTHERS THEN
      DBMS_OUTPUT.PUT_LINE('Sin permisos de V$ para ' || v_usuario ||
                           ' (el docente proyecta el monitoreo)');
    END;
  END LOOP;
END;
/

-- Verificación
-- ---------------------------------------------------------------------
SELECT username, account_status, created
  FROM dba_users
 WHERE username LIKE 'P__'
 ORDER BY username;

-- =====================================================================
-- Bases de Datos 2 · Concurrencia, transacciones y bloqueos
-- 02_sesion_A.sql          >>>  VENTANA A  <<<
--
-- NO ejecute este archivo de corrido. Cada bloque dice PASO n:
-- ejecútelo cuando le toque, alternando con la ventana B.
--
-- Verifique primero que el autocommit está APAGADO.
-- =====================================================================

-- Quién soy
SELECT 'SESIÓN A' AS ventana, SYS_CONTEXT('USERENV','SID') AS sid FROM dual;


-- #####################################################################
-- EJERCICIO 1 — Lectura consistente: los lectores no se bloquean
-- #####################################################################

-- PASO 1  (A)
SELECT id_cuenta, titular, saldo FROM cuenta ORDER BY id_cuenta;

-- PASO 2  (A)  Retiro 200.000 de la cuenta 1, SIN confirmar
UPDATE cuenta SET saldo = saldo - 200000 WHERE id_cuenta = 1;
SELECT id_cuenta, saldo FROM cuenta WHERE id_cuenta = 1;
--> A ve 800.000: dentro de su transacción, ve sus propios cambios.

-- ... ahora vaya a la ventana B, PASO 3 ...

-- PASO 5  (A)  Confirmo
COMMIT;

-- ... ventana B, PASO 6 ...

-- CONCLUSIÓN DEL EJERCICIO 1
--   B nunca se bloqueó y nunca vio el saldo a medias. Vio el valor
--   anterior hasta que A confirmó. Eso es la lectura consistente:
--   Oracle reconstruye la versión de los datos desde el UNDO.
--   En Oracle, los lectores NO bloquean a los escritores ni al revés.


-- #####################################################################
-- EJERCICIO 2 — Bloqueo de fila y actualización perdida
-- #####################################################################

-- PASO 1  (A)
UPDATE cuenta SET saldo = saldo - 100000 WHERE id_cuenta = 2;
--> Responde de inmediato: A tomó el bloqueo de esa fila.

-- ... ventana B, PASO 2: intenta actualizar la MISMA fila y se queda esperando ...

-- PASO 4  (A)  Mientras B espera, mire quién bloquea a quién:
--   (si no tiene permisos sobre V$, lo proyecta el docente)
SELECT sid, serial#, status, blocking_session, event, seconds_in_wait
  FROM v$session
 WHERE username = USER
 ORDER BY sid;

-- PASO 5  (A)  Libero
COMMIT;

-- ... ventana B, PASO 6 ...

-- PASO 8  (A)  ¿Cuánto quedó?
SELECT id_cuenta, titular, saldo FROM cuenta WHERE id_cuenta = 2;
--> Empezó en 500.000. A restó 100.000 y B restó 50.000.
--  ¿Quedó en 350.000, o en 450.000? Discútanlo antes de mirar.


-- #####################################################################
-- EJERCICIO 3 — Evitar la actualización perdida
-- #####################################################################

-- --- 3.a  Estrategia PESIMISTA: bloqueo explícito con FOR UPDATE ---

-- PASO 1  (A)
SELECT id_cuenta, saldo FROM cuenta WHERE id_cuenta = 3 FOR UPDATE;
--> Leo Y bloqueo. Nadie más podrá tocar esta fila hasta mi COMMIT.

-- ... ventana B, PASO 2 ...

-- PASO 4  (A)
UPDATE cuenta SET saldo = saldo - 50000 WHERE id_cuenta = 3;
COMMIT;

-- ... ventana B, PASO 5 ...


-- --- 3.b  Estrategia OPTIMISTA: número de versión ---
-- Nadie bloquea nada; se detecta el choque al escribir.

-- PASO 6  (A)  Leo el saldo y la versión
SELECT id_cuenta, saldo, version FROM cuenta WHERE id_cuenta = 1;
--> Anote el número de version que ve.  Suponga que es 0.

-- ... ventana B, PASO 7: lee la misma fila y actualiza primero ...

-- PASO 9  (A)  Intento actualizar con la versión que leí
UPDATE cuenta
   SET saldo   = saldo - 30000,
       version = version + 1
 WHERE id_cuenta = 1
   AND version  = 0;          -- <-- la versión que leí en el PASO 6
COMMIT;

SELECT 'Filas afectadas: ver el mensaje del UPDATE' AS nota FROM dual;
--> Si dice "0 filas actualizadas", alguien cambió la fila entre mi
--  lectura y mi escritura. La aplicación debe releer y reintentar,
--  o avisarle al usuario. Nada se perdió en silencio.

SELECT id_cuenta, saldo, version FROM cuenta WHERE id_cuenta = 1;


-- #####################################################################
-- EJERCICIO 4 — FOR UPDATE: NOWAIT, WAIT y SKIP LOCKED
-- #####################################################################

-- PASO 1  (A)  Reservo la silla 5 y me quedo con el bloqueo
SELECT id_silla, fila, numero, estado FROM silla WHERE id_silla = 5 FOR UPDATE;

-- ... ventana B, PASOS 2, 3 y 4 ...

-- PASO 5  (A)  Confirmo y libero
UPDATE silla SET estado = 'RESERVADA', reservada_por = 'Sesión A' WHERE id_silla = 5;
COMMIT;

-- PASO 6  (A)  La cola de trabajos: dos operarios sin pisarse
--   SKIP LOCKED ignora las filas que otro ya tiene bloqueadas.
SELECT id_trabajo, payload
  FROM trabajo
 WHERE estado = 'PENDIENTE'
 ORDER BY id_trabajo
 FETCH FIRST 3 ROWS ONLY
   FOR UPDATE SKIP LOCKED;

-- ... ventana B, PASO 7: pide otros 3 y recibe trabajos DISTINTOS ...

-- PASO 8  (A)
UPDATE trabajo SET estado='PROCESADO', procesado_por='A'
 WHERE id_trabajo IN (SELECT id_trabajo FROM trabajo
                       WHERE estado='PENDIENTE' AND ROWNUM <= 0);
-- (en la práctica se actualizan los ids que devolvió el SELECT anterior)
COMMIT;


-- #####################################################################
-- EJERCICIO 5 — Interbloqueo (deadlock)
-- #####################################################################

-- PASO 1  (A)  Bloqueo la cuenta 1
UPDATE cuenta SET saldo = saldo - 1000 WHERE id_cuenta = 1;

-- ... ventana B, PASO 2: bloquea la cuenta 2 ...

-- PASO 3  (A)  Ahora pido la cuenta 2, que B tiene tomada  -> me quedo esperando
UPDATE cuenta SET saldo = saldo + 1000 WHERE id_cuenta = 2;

-- ... ventana B, PASO 4: pide la cuenta 1, que yo tengo -> ciclo cerrado ...

--> A los pocos segundos, UNA de las dos sesiones recibe:
--     ORA-00060: deadlock detected while waiting for resource
--  Oracle detecta el ciclo y sacrifica una de las dos sentencias.
--  La transacción NO se deshace entera: solo esa sentencia. La sesión
--  víctima queda con su transacción abierta y debe decidir.

-- PASO 5  (A)  Deshago todo
ROLLBACK;

-- CÓMO SE EVITA
--   Accediendo a los recursos SIEMPRE en el mismo orden. Si las dos
--   sesiones hubieran tomado primero la cuenta 1 y después la 2, no
--   habría ciclo posible.


-- #####################################################################
-- EJERCICIO 6 — SAVEPOINT y el COMMIT implícito del DDL
-- #####################################################################

-- PASO 1  (A)
INSERT INTO asiento VALUES (1, 'Asiento uno', 100);
SAVEPOINT despues_del_uno;

INSERT INTO asiento VALUES (2, 'Asiento dos', 200);
INSERT INTO asiento VALUES (3, 'Asiento tres', 300);
SELECT * FROM asiento ORDER BY id_asiento;      --> 3 filas

ROLLBACK TO SAVEPOINT despues_del_uno;
SELECT * FROM asiento ORDER BY id_asiento;      --> queda 1 fila
--> El rollback parcial deshace hasta el savepoint, no toda la transacción.
--  La transacción sigue abierta.

-- PASO 2  (A)  LA TRAMPA: una sentencia DDL confirma sola
CREATE TABLE basura_temporal (x NUMBER);
--> Ese CREATE hizo COMMIT de todo lo que había pendiente.

ROLLBACK;
SELECT * FROM asiento ORDER BY id_asiento;
--> El asiento 1 sigue ahí: el ROLLBACK ya no tenía nada que deshacer.
--  Regla: nunca mezcle DDL dentro de una transacción de negocio.

DROP TABLE basura_temporal PURGE;


-- #####################################################################
-- EJERCICIO 7 — Nivel de aislamiento SERIALIZABLE
-- #####################################################################

-- PASO 1  (A)
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT id_cuenta, saldo FROM cuenta WHERE id_cuenta = 3;
--> A partir de aquí, A ve una foto congelada del momento en que empezó.

-- ... ventana B, PASO 2: modifica la cuenta 3 y confirma ...

-- PASO 3  (A)  Vuelvo a leer
SELECT id_cuenta, saldo FROM cuenta WHERE id_cuenta = 3;

-- EJERCICIO 2 — Bloqueo de fila y actualización perdida
-- #####################################################################

-- ... A hizo su PASO 1 y tiene bloqueada la cuenta 2 ...

-- PASO 2  (B)  Intento actualizar LA MISMA fila
UPDATE cuenta SET saldo = saldo - 50000 WHERE id_cuenta = 2;
--> ESTA SENTENCIA NO RESPONDE. Queda esperando el bloqueo de A.
--  Déjela corriendo y observe. No la cancele.

--   mire cómo se ve el bloqueo desde el diccionario.

-- PASO 6  (B)  Ya respondió. Confirmo
COMMIT;

--> 500.000 - 100.000 - 50.000 = 350.000.

--

SELECT id_cuenta, saldo FROM cuenta WHERE id_cuenta = 3;

   SET saldo   = saldo - 10000,
       version = version + 1
 WHERE id_cuenta = 1

-- ... A intenta su UPDATE con version = 0 y actualiza 0 filas ...
--> Nadie se bloqueó en ningún momento, y aun así no se perdió nada.

SELECT USER                                   AS usuario,
       SYS_CONTEXT('USERENV','SID')           AS sid,
       SYS_CONTEXT('USERENV','SESSION_USER')  AS sesion_de
  FROM dual;

-- ---------------------------------------------------------------------
-- 1. Limpieza previa
-- ---------------------------------------------------------------------
BEGIN
  FOR t IN (SELECT table_name FROM user_tables
             WHERE table_name IN ('MOVIMIENTO','CUENTA','ASIENTO',
                                  'SILLA','TRABAJO')) LOOP
    EXECUTE IMMEDIATE 'DROP TABLE '||t.table_name||' CASCADE CONSTRAINTS PURGE';
  END LOOP;
END;

-- ---------------------------------------------------------------------
-- 2. Caso bancario: el clásico de las transacciones
-- ---------------------------------------------------------------------
CREATE TABLE cuenta (
  id_cuenta   NUMBER        NOT NULL,
  titular     VARCHAR2(40)  NOT NULL,
  saldo       NUMBER(14,2)  NOT NULL,
  version     NUMBER        DEFAULT 0 NOT NULL,   -- para el bloqueo optimista
  CONSTRAINT pk_cuenta PRIMARY KEY (id_cuenta),
  CONSTRAINT ck_saldo  CHECK (saldo >= 0)
);

CREATE TABLE movimiento (
  id_mov      NUMBER GENERATED BY DEFAULT AS IDENTITY,
  id_cuenta   NUMBER        NOT NULL,
  fecha_mov   TIMESTAMP     DEFAULT SYSTIMESTAMP NOT NULL,
  concepto    VARCHAR2(60)  NOT NULL,
  valor       NUMBER(14,2)  NOT NULL,
  CONSTRAINT pk_movimiento PRIMARY KEY (id_mov),
  CONSTRAINT fk_mov_cuenta FOREIGN KEY (id_cuenta) REFERENCES cuenta
);

COMMIT;

-- ---------------------------------------------------------------------
-- 3. Caso de reserva de sillas: para FOR UPDATE y SKIP LOCKED
-- ---------------------------------------------------------------------

  id_silla    NUMBER        NOT NULL,
  fila        VARCHAR2(2)   NOT NULL,
  numero      NUMBER        NOT NULL,
  estado      VARCHAR2(12)  DEFAULT 'LIBRE' NOT NULL,
  reservada_por VARCHAR2(40),
  CONSTRAINT pk_silla PRIMARY KEY (id_silla),
  CONSTRAINT ck_silla_estado CHECK (estado IN ('LIBRE','RESERVADA','VENDIDA'))
);

INSERT INTO silla (id_silla, fila, numero)
SELECT level, CHR(65 + TRUNC((level-1)/10)), MOD(level-1,10)+1
  FROM dual CONNECT BY level <= 30;
COMMIT;
